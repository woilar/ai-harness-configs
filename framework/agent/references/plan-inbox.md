# Ревью планов в Plannotator Inbox

Читать после создания содержательного черновика, изменения редакции решения,
при получении замечаний и восстановлении известной задачи с Inbox. Локальное
состояние — [task-state.md](task-state.md), состав плана — [planning.md](planning.md).
Отложенные находки используют отдельный протокол [inbox.md](inbox.md).

## Файл, редакция и тред

Единственный источник истины — `.ai-plans/<task-id>/plan.md` текущего worktree.
Inbox содержит обсуждение фичи и неизменяемые снимки отправленных редакций,
а не второй редактируемый план. Не создавать отдельный MD ради отправки.

После сохранения содержательного черновика автоматически отправить существующий
`plan.md` вложением через встроенный `plannotator_inbox`. Содержательный черновик
содержит цель, предложенное решение, границы, шаги, проверки и явно открытые вопросы;
он не обязан быть уже утверждён. Пустой шаблон не отправлять. Отдельной команды
«отправь план» не ждать: этот процесс уже поручен пользователем.

Одна задача — один тред. В первом сообщении указать безопасное имя фичи, task ID,
редакцию и ключ доставки. Все последующие редакции и ответы направлять в этот же
тред; не создавать новый при смене роли, модели, сессии или ветки. Один task ID
в разных worktree не доказывает тождество задач: сверять сохранённую привязку.

Редакция решения — монотонный номер в MD. Изменение требований, подхода, контрактов,
границ, шагов или критериев проверки повышает номер и требует нового вложения.
Прогресс, фактические результаты проверок и точка продолжения номера не меняют
и повторного вложения не требуют. Не сравнивать только хеш всего файла для решения
о повторной отправке: он меняется и при обновлении прогресса.

## Локальный receipt

Рядом с планом вести `.ai-plans/<task-id>/inbox.json`, также исключённый из Git.
Это только связь с доставкой, не копия решения, прогресса или approval. До вызова
сохранить стабильный `task_key` (UUID), номер редакции, SHA-256 точных байтов MD и
`delivery_key` (новый UUID для новой редакции; тот же ключ при повторе). Пример:

```json
{
  "schema_version": 1,
  "task_key": "<UUID задачи>",
  "worktree": "<абсолютный корень worktree>",
  "task_id": "<task-id>",
  "plan_path": ".ai-plans/<task-id>/plan.md",
  "thread_id": null,
  "thread_url": null,
  "deliveries": [
    {
      "revision": 1,
      "file_sha256": "<SHA-256 отправляемого MD>",
      "delivery_key": "<UUID этой доставки>",
      "status": "not_sent",
      "message_id": null,
      "message_url": null,
      "sent_at": null,
      "error": null
    }
  ]
}
```

`deliveries` сохраняет соответствие всех отправленных редакций их сообщениям,
чтобы поздний комментарий не привязался к последнему сообщению по ошибке.
После подтверждённого успеха записать `status: sent`, фактические thread/message ID,
возвращённые URL (иначе null) и время. Не выдумывать ID/URL. Запись атомарная с
перечитыванием; symlink, чужие правки и конфликты обрабатывать как для плана.
Если receipt не удалось сохранить до вызова, не отправлять вслепую.

Сверить байты файла непосредственно перед вложением с сохранённым SHA-256.
Если MD изменился во время отправки, receipt относится только к реально
отправленным байтам; текущий MD не объявлять доставленным. Не прикреплять другую
редакцию под прежним ключом. Несколько редакций до первой успешной отправки можно
свести к текущей; старые неотправленные записи сохранить со статусом `superseded`.
Запись `unconfirmed` не заменять этим статусом: сначала выяснить результат. Пока
не выяснена первая отправка, не отправлять новую редакцию в новый тред.

## Только встроенный инструмент

Перед использованием прочитать актуальную схему `plannotator_inbox`. Проверить,
что поддерживаются вложение существующего MD, создание/продолжение треда и нужное
чтение/поиск. Имена операций и полей брать из схемы, не выдумывать. Не запускать
Inbox CLI (включая `--help`), HTTP, браузерную отправку, прямое чтение внутренних
файлов Inbox или другой транспорт. Обычный annotate не заменяет Inbox.
Не устанавливать плагины и не менять подключения/права ради обхода ошибки.

Сначала сохранить локальный MD. При отсутствии инструмента, действия или явной
ошибке доставки оставить его на месте, записать `not_sent` и причину, сообщить
«Inbox: не отправлено». Не заявлять отправку и не откатывать план.

Перед вызовом с возможной доставкой записать `status: unconfirmed`;
таймаут, перезапуск до receipt и неоднозначный результат означают
«Inbox: доставка не подтверждена». Перед повтором искать точный `delivery_key`
встроенным инструментом, сверять task_key, редакцию, вложение/хеш и тред.
Найденную доставку записать, а не отправлять снова. При невозможности проверить
не повторять автоматически и не создавать второй тред. Подтверждённую неудачу
можно повторить после восстановления доступности с тем же ключом.

Если отправка подтверждена, но запись receipt не удалась, сообщить отдельно успех
отправки и ошибку локальной записи; восстановить receipt через встроенный инструмент
до повтора. Успех без обязательных ID считать неподтверждённым для безопасного повтора.
При возобновлении читать только receipt выбранной задачи: `sent` не пересылать,
`unconfirmed` сверить, новую редакцию отправить в сохранённый тред.

## Замечания и утверждение

Читать сообщения выбранного треда через встроенный инструмент. До правки MD
сопоставить замечание с message ID/редакцией из receipt и текущей редакцией решения.
Замечание к старой редакции проверить на актуальность; конфликтующие или неясно
привязанные замечания уточнить в том же треде, не применять автоматически.
Применённые изменения сохранять в исходном MD, повышать редакцию при изменении
решения и прикладывать обновлённый файл в тот же тред.

Только явное утверждение пользователя конкретной редакции фиксировать в разделе
«Подтверждение редакции» исходного MD с указанием редакции и сообщения-основания.
Неясное «ок» без привязки не распространять на текущую редакцию. Send feedback,
комментарии, прочтение, закрытие треда и молчание не являются approval.
Утверждение старой редакции не утверждает изменённое решение.
Approval не разрешает реализацию без отдельного запроса; утверждение и исполнение
учитывать отдельно, не дублировать их в receipt.

## Сохранность

Вложение плана — явно разрешённое исключение из локального хранения. Передавать
только разрешённый план; запреты проекта на передачу и секреты имеют приоритет.
При конфликте сохранить допустимый локальный MD и сообщить причину без отправки.
Разрешение прикреплять план не распространяется на код, diff, конфиги и логи.
Отложенные находки по inbox.md по-прежнему отправляются только кратким текстом.

После удаления worktree вложение остаётся снимком в Inbox. Не обещать синхронизацию,
резервное восстановление или автоматическую реализацию. Восстановление локального
плана из вложения требует явного запроса и проверки редакции; снимок сам по себе
не становится новым источником истины.
