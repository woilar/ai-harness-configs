# Валидация и принятие

Читать до проверок/предъявления diff и при /deferred. При записи результата использовать [task-state.md](task-state.md), при выявленном пробеле — [learning-journal.md](learning-journal.md).

### Валидация и reverse explain

- Выбирать проверки по масштабу и последствиям; не писать тесты ради ритуала или зеркального повторения реализации. До запуска использовать прогноз пользователя, если он уже дан для этой редакции — не спрашивать снова. Непроведённую проверку не объявлять успешной; невозможность прогона зафиксировать и согласовать как ограничение.
- Reverse explain проверяет понимание конкретного изменения, а не способность самостоятельно реализовать аналог. Для выявленного пробела выбирать практику по навыку: механизм → прогноз; проектирование → подход и компромисс; диагностика → различающий эксперимент; реализация → собственный существенный фрагмент; изменение системы → адаптация к новому требованию. Не требовать все формы сразу и не блокировать понятную рабочую правку полным экзаменом. Проверку навыка выполнять в Coach на независимом примере.
- После реализации показать raw diff, границы и фактический статус проверок, не объясняя механизм за пользователя. Пользователь описывает поведение, почему так, как проверено, ограничения и непонятное. **До окончания попытки не подсказывать, не подтверждать и не поправлять**; результаты проверок сообщать как факты без готового объяснения.
- Без объяснения существенной части задача не завершена: Coach разбирает фрагмент, журнал фиксирует пробел/упражнение; затем новая попытка с отметкой помощи. Корректный проверенный код не откатывать только из-за учебного пробела; реальный дефект исправлять по последствиям. Новое существенное изменение требует нового объяснения изменённой части.
- Пока ожидается первая попытка в текущем диалоге, статус — «ожидается reverse explain», не «отложен». Только при явной отсрочке, отказе или завершении сессии сохранить «reverse explain отложен» и «реализация выполнена, принятие/проверка понимания не завершены»; не принуждать к продолжению и не объявлять завершение. Большой diff разбирать по согласованным логическим шагам.

### Diff Review и ленивая загрузка Java-справочника

После шага кодинга, в фазе валидации, проверить только релевантное:
1. Изменение наблюдаемого поведения.
2. Входы/выходы, ошибки, side effects и границы контрактов.
3. Новые зависимости, потоки, транзакции, кэши или конфигурацию.
4. Повторное и параллельное выполнение.
5. Возможность отката.
6. Тест/сценарий, подтверждающий нужное свойство, и его ограничения.
7. Оставшееся непонимание после попытки пользователя — устранить до принятия.

**`references/java-impact-checklist.md` не читать при старте, согласовании или учебном объяснении. Обращаться к нему только на этапе Diff Review после шага кодинга**, открывая нужные разделы, не весь файл. До кода риски обсуждать по фактам и документации, без загрузки этого справочника. Нерелевантные пункты отметить одной короткой строкой; одних зелёных тестов недостаточно.

### /deferred: ручная проверка отложенного reverse explain

Команда вручную переводит фокус в фазу валидации отложенных задач; поэтому прочитать этот раздел и правила валидации в этом файле. Искать **только** «reverse explain отложен» в планах `.ai-plans/` выбранного worktree и доступных прежних agreement; для исключения без MD использовать доступную точную запись чата. Если доступа/записи нет — сообщить это, не придумывать задачи и не начинать неограниченный поиск по всем проектам.

1. Показать найденные задачу/версию diff, ссылку или запись, проверку и открытый статус. Сверить текущий код с отложенной редакцией; не принимать другой diff по старому объяснению.
2. При нескольких задачах предложить пользователю выбрать одну. Дать raw diff без объяснения, дождаться самостоятельной попытки; затем применить обычную валидацию и Diff Review.
3. При существенном непонимании передать в Coach через handoff; при успехе закрыть отложенный статус и перейти к фиксации. Не считать команду разрешением менять код или принять задачу без попытки.

Нет фоновой памяти/напоминаний и автоматического сканирования при начале сессии. Отложенный статус хранится в разделе состояния текущего MD-плана, краткой рабочей записи, прежнем agreement или точной записи чата. Если reverse explain отложен, но пробел ещё не выявлен, сохранить статус в существующей записи договорённостей или чате; не выдавать непроверенное понимание за пробел. Выявленный пробел обязательно сохранить в учебном журнале, включая Low Energy/Fast-Track. Пользователь сам вызывает `/deferred` и при необходимости предоставляет запись.
