# Планирование и ревью

Читать при начале/пересмотре нетривиальной работы, а не при обычном вопросе.
До записи рабочего документа прочитать [task-state.md](task-state.md), при создании плана — [plan-template.md](plan-template.md).

## Согласование решения

- Инженерный подход формулирует пользователь: поведение, существенный механизм, компромиссы, гарантии и границы. Агент исследует факты, задаёт вопросы и показывает риски. Использовать уже высказанную гипотезу; неполный план не доказывает отсутствия основы. При подтверждённом отсутствии основы — Coach.
- Агент может предложить техническую последовательность внутри выбранного подхода: порядок правок согласованных участков, однотипных вызовов, фикстур и проверок. Обозначить автора разбиения; если декомпозиция — учебная цель пользователя, оставить её ему.
- Новый выбор поведения, контрактов, данных, доступа, конкурентности, зависимостей или отката вернуть в обсуждение. Не выдавать предложение агента за решение пользователя. Готовый дизайн допустим в Coach для другой учебной задачи.
- До кода понятны цель, критерии, подход, обычный и ошибочный сценарии, границы шага, гарантии, ограничения, миграции и проверки. Пользователь своими словами объясняет существенный механизм и компромисс; уже зафиксированное объяснение использовать без повторного экзамена.

## Создание плана

Определить корень текущего worktree. Создать `.ai-plans/<task-id>/plan.md` по правилам локального состояния. Task ID — безопасное короткое имя с уникальным суффиксом, например `payment-retry-20261105-01`; сначала проверить существующие планы на ту же цель. Не создавать дубли и не переименовывать выбранную задачу при смене роли. Вне выбранного worktree ничего не создавать.

План — единый документ решения и состояния работы. В нём цель, требования, факты/предположения, решения пользователя, предложения агента отдельно, открытые вопросы, шаги `P1`, `P2` и т. д., зависимости, границы и проверки. ID шагов сохранять при вставке/изменении порядка; заменённые шаги обозначать явно.

Обновлять черновик по мере принятия решений и перед handoff. Обычные вопросы и независимые учебные упражнения сами по себе рабочего плана не требуют. Fast-Track не требует полного плана или ревью Plannotator; его состояние при необходимости сохраняется кратко по task-state.md.

## Ревью через Plannotator

По просьбе пользователя или когда черновик готов к рассмотрению открыть точный MD через доступную интеграцию/CLI Plannotator. Проверить инструменты и локальную справку установленной версии, использовать результат ревью в этой сессии. Не устанавливать плагин молча. Если интеграции нет или запуск не удался, назвать ограничение и дать существующий файл для IDEA/чата; успешное открытие/approval не выдумывать.

Замечания применять итерациями. Редакция относится к разделу решения: требованиям, контрактам, границам, шагам и проверкам. Фиксировать явное подтверждение именно показанной редакции. Send feedback, закрытие окна, отсутствие комментариев и молчание не означают утверждение. Существенные открытые вопросы не скрывать. Утверждение плана само по себе не запрашивает реализацию.

## Исполнение и пересмотр

После утверждения не переносить и не дублировать план: Executor читает тот же MD и выполняет прямо запрошенный согласованный шаг. Прогресс, результаты проверок, блокеры, reverse explain, принятие и следующий шаг записывать в раздел состояния этого документа. Изменение только фактического прогресса не меняет редакцию решения и не требует нового approval.

Новый существенный факт останавливает затронутую часть. Обновить редакцию решения в том же файле, отметить причины и затронутые шаги; сохранить выполненное и прежнее основание подтверждения как историю. Изменённые решения отдать на ревью. Старое approval не распространять на изменённую часть; независимая работа допустима внутри прежних подтверждённых границ. Обновление прогресса не использовать для скрытого изменения контракта.

## Большая работа

Общий план задаёт цель, сохраняемое поведение, крупные этапы и стратегию проверок. Подробно согласовывать ближайший этап; будущие этапы явно помечать как требующие детализации. При необходимости у этапа свой MD в каталоге задачи; общий план содержит указатель и краткий итог, не вторую редактируемую копию его состояния. Следующий этап детализировать с учётом результатов и отдать на ревью.

Зависимости вести по стабильным ID шагов. Для обзора читать текущий план и нужный этап: что принято, что реализовано/проверено, что заблокировано и следующий шаг. Поиск других планов выполняется по запросу, а не автоматически при старте.
