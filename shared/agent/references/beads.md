# Beads: рабочая память

Читать до первого обращения к базе, включая Fast-Track. Планирование описано в [planning.md](planning.md), восстановление — в [handoff.md](handoff.md), принятие — в [validation.md](validation.md).

### Beads: проект, запись и восстановление

**Определение базы.** При первом чтении или записи в сессии выполнить из рабочей папки `git rev-parse --path-format=absolute --git-common-dir`. Канонический абсолютный путь общего Git-каталога — ключ в JSON-объекте `~/ai/beads/projects.json`; значение — абсолютный путь отдельной базы, например `/Users/andrey/ai/beads/payments`. Все worktree одного клона получают один ключ; другой клон, submodule или репозиторий — отдельный ключ. Не объединять их по имени папки или URL remote. После смены рабочей папки повторить определение. При ошибке Git или неоднозначном контексте остановить операции Beads и уточнить проект.

Если предполагается одновременная запись нескольких сессий/worktree в одну базу, использовать серверный режим Dolt: проверить справку установленной версии `bd init --server` и требования к `dolt sql-server`, настроить общий локальный сервер и доступ к нему. Embedded-режим по умолчанию не считать достаточным для нескольких одновременных писателей. Проверить существующий режим до начала параллельной работы; не переинициализировать и не мигрировать существующую базу молча — сначала сохранить данные и согласовать переход. При недоступном сервере сообщить об ограничении, не запускать параллельные записи в embedded-базу. Это настройка Beads, а не расширение OMP.

Если привязки нет, автоматически зарегистрировать отдельную базу в `~/ai/beads/<имя>-<digest>/`, где digest — полный SHA-256 канонического ключа в UTF-8, имя — безопасное имя репозитория для читаемости. Не использовать одну глобальную базу. Проверить существование CLI через `bd version`, затем локальную справку `bd init --help`: инициализировать только новое хранилище с явным BEADS_DIR, без записи инструкций/хуков в рабочий проект и без настройки remote/sync; использовать поддерживаемые установленной версией опции. Если это невозможно или каталог уже содержит неизвестные данные — сообщить и уточнить, не переинициализировать. Отсутствующий CLI не устанавливать молча.

Реестр создавать только при отсутствии; повреждённый JSON, не-объект, не-абсолютные пути или повторное использование базы другим ключом считать конфликтом. Не перезаписывать другие привязки. Добавлять запись после успешной проверки базы, через временный файл и атомарную замену под эксклюзивной блокировкой; под блокировкой перечитать реестр и проверить отсутствие конкурентного изменения. Не снимать чужую/оставшуюся блокировку автоматически. Если безопасная запись недоступна — остановиться и сообщить. При перемещении основного клона не угадывать старую привязку и не создавать новую базу, если пользователь сообщил о переезде: сначала согласовать обновление ключа. После записи перечитать реестр и подтвердить фактический путь.

Во всех командах задавать BEADS_DIR для одного вызова; пути/текст передавать безопасно, без shell-интерполяции пользовательского содержимого. Не экспортировать одну базу на весь компьютер. Не обращаться напрямую к внутренним файлам БД; использовать установленный `bd`, актуальные `--help`, `bd create`, `bd show`, `bd update`, `bd search`, `bd list`, `bd ready`, `bd close`. Не предполагать совместимость флагов разных версий. В BB/ACP команды выполняет OMP через доступный shell с обычными разрешениями; отказ не обходить. Не запускать `bd setup`, устанавливающий чужие инструкции/хуки, вместо правил этого фреймворка.

**Создание и запись.** Создавать задачу автоматически при содержательном планировании конкретной работы или начале исполнения, даже до готового плана. Если ID уже известен — использовать его после проверки проекта. Иначе точечно искать дубли по цели/компоненту, включая завершённые задачи: закрытая похожая задача не означает, что новая работа уже выполнена. Несколько подходящих активных задач — уточнить выбор. Не превращать обычные вопросы и отдельные учебные упражнения в рабочие тикеты. Кратко сообщить фактический ID после успешного создания.

Copilot ведёт черновик и ревью MD по [planning.md](planning.md); в Beads до утверждения хранит привязку и точку остановки, после — проверенные общие решения и шаги. Executor записывает согласованный шаг, фактический прогресс, результаты проверок и отклонения. Coach сохраняет краткий итог обучения и точку возврата в текущую рабочую задачу; карточки пробелов и упражнения остаются в `~/ai/learning/`. Смена роли сохраняет общую задачу и текущий дочерний шаг, не создаёт дубль и не разрешает кодинг; учебная сессия сама по себе не завершает рабочую задачу.

Обновлять запись после принятого решения/изменения требований, законченного шага, проверки и перед handoff или явным завершением сессии. Читать текущую версию перед изменением; не заменять чужие/параллельные обновления устаревшей копией. При конфликте сохранить обе позиции и уточнить согласование. Не обещать транзакционность последовательности CLI-вызовов; для одновременной работы над одной записью согласовать одного писателя. Сохранять номер редакции и явное подтверждение именно этой редакции, автора технической последовательности, контекст ветки/worktree и исходной версии. Новое уточнение меняет только затронутые пункты; предложения/подозрения не повышать до решений/фактов. Не копировать рабочий код, diff, секреты, конфигурации и логи; достаточно разрешённых текстовых указателей и безопасного описания требований/результатов. При запрете проекта на внешнее хранение соблюдать его и сообщить конфликт.

Посторонние баги/улучшения сохранять отдельными задачами: симптом, место, свидетельства или степень уверенности, следующий шаг проверки и связь с текущей работой, если уместна. Сначала точечно проверить дубли. Не начинать исправление без запроса. Если находка блокирует текущий контракт, явно пересмотреть затронутый шаг, а не прятать проблему в backlog. В конце итерации кратко назвать созданные/обновлённые задачи; не создавать записи ради отчётности.

Различать реализацию, фактические проверки и принятие. Пока ожидается reverse explain — принятие открыто; при явной отсрочке записать «reverse explain отложен». Не закрывать задачу только по зелёным тестам. Закрывать после применимых критериев фреймворка; найденные отдельные задачи остаются открытыми. При ошибке CLI/прав/БД или записи сообщать «задача/обновление не сохранены», сохранять дельту в чате, не сообщать выдуманный ID и не создавать независимую копию. После восстановления сначала сверить запись, затем применить пропущенную дельту без дубля.
